3D Diagnostix · threeddx3 · operations

Runbook

From an empty database to a verified, reconciled threeddx3 and its anonymized twin on the Dokku host, then dumps, users, restore elsewhere and day-two care. Every command matches the script it calls; placeholders are in UPPER_CASE or ….

0 · Before you start

read once

Non-negotiables

  • Use only tools/remote.py for the host: one multiplexed ssh connection. If ssh fails, stop — never retry in a loop; repeated logins lock the account for hours.
  • The tools refuse every database except threeddx3, threeddx3_anony and threeddx3_scratch_*. Do not weaken those guards. Verification work happens on scratch databases.
  • The legacy MySQL connect is read, never written.
  • etl/connections.env is git-ignored; ~/.3ddx3/ on the host (secrets.env with SODIUM_KEY, users.env with issued passwords) is mode 600 and never copied off the host.
  • No PHI and no key material in logs, tickets or chat. The ETL never logs decoded dates of birth.

Commands below run from v3/ on the workstation after set -a; . etl/connections.env; set +a. tools/remote.py run '…' executes in /var/tmp/3ddx3 on the host with the server's connections.env and ~/.3ddx3/secrets.env sourced and python3 = /var/tmp/etlvenv/bin/python (3.12). Commands marked (root) run in a root shell on the host because they read the Postgres service password from /var/lib/dokku/services/postgres/shared-postgres/PASSWORD and use psql / pg_dump inside the container, exactly as ops/cleanup_and_retire_v1_v2.sh does.

1 · Build the schema

minutes
1

Push the code

python3 tools/remote.py sync
2

Rehearse on a scratch database

Scratch databases are disposable: --recreate-db needs no confirmation there.

python3 tools/remote.py run 'python3 tools/apply_migrations.py --db threeddx3_scratch_all --recreate-db'
3

Build threeddx3 from empty

38 files, each in its own transaction, each recorded with its SHA-256 in public.schema_migrations. ssh has no terminal, so give the drop confirmation with --yes. An authoritative load always starts here: append-only history rejects DELETE, so no stage is re-runnable on a populated database.

python3 tools/remote.py run 'python3 tools/apply_migrations.py --db threeddx3 --recreate-db --yes'
python3 tools/remote.py run 'python3 tools/apply_migrations.py --db threeddx3 --status'

CHANGED SINCE APPLIED in --status means a file was edited after it ran: rebuild, never patch the tracker.

2 · Verify

minutes
1

Static checks (workstation, no database)

Regenerates this document set after the checks pass; --server adds the checks below in one ssh session; --refresh-catalog rebuilds threeddx3_scratch_all and re-extracts docs/_catalog.json first.

python3 tools/build_docs.py --check
python3 tools/build_docs.py --refresh-catalog --server
2

Catalog conventions

tools/check_v3_catalog.py reads only the catalog. FAIL: an object without a comment, a nullable column whose comment does not say what NULL means, a table without a primary key, a wrongly prefixed constraint/index/trigger/function, a 63-character (truncated) name, SET NULL on a NOT NULL column. WARN: an FK not covered by an index, a table without tenant_id not on the global list, a comment under 25 characters. Exit 1 on any FAIL (or any WARN with --strict).

python3 tools/remote.py run 'python3 tools/check_v3_catalog.py --db threeddx3_scratch_all'
3

ON CONFLICT targets

tools/check_on_conflict.py finds every INSERT … ON CONFLICT in the ETL and has PostgreSQL plan it against the empty schema, so a conflict target that matches no unique index fails in milliseconds instead of hours into a load (v2 defect 39). Python 3.12 syntax: run it on the host.

python3 tools/remote.py run 'python3 tools/check_on_conflict.py --db threeddx3_scratch_all'
4

Runtime tests

tests/runtime_tests.sql runs in one transaction that ends in ROLLBACK (the runner refuses a script containing COMMIT), so it is safe even on threeddx3. It proves the rules live: fail-closed RLS (unset / wrong tenant → 0 rows, INSERT rejected), role grants, PHI only through the logged functions, audit redaction and the hash chain (including a tamper test), append-only and approved-record immutability, voucher arithmetic, pricing. Needs a superuser connection (it uses SET ROLE). Exit 0 = every assertion passed.

python3 tools/remote.py run 'python3 tests/run_runtime_tests.py --db threeddx3_scratch_all --quiet'

3 · The authoritative run

hours
1

Preconditions

  • The MySQL snapshot to migrate is restored into dokku shared-mysql as connect (root): sudo bash ops/restore_mysql_connect.sh /var/tmp/connect-YYMMDD.sql.zst (strips DEFINER clauses, no binlog, stops on the first real error).
  • threeddx3 rebuilt from empty (phase 1) and verified (phase 2).
  • ~/.3ddx3/secrets.env holds SODIUM_KEY for the date-of-birth decoder. Values it cannot decrypt are quarantined (clinical.patient_identities.dob_status), never guessed.
  • Pick the snapshot label: ETL_SOURCE_SNAPSHOT (default connect-261013-0300) is recorded in audit.migration_runs.source_snapshot with the code checksum.
2

Start it detached

ops/run_etl_detached.sh <target_db> <log_name> <stage> [stage …] runs each stage with etl/run_etl.py --only, after sourcing the env files; it exports ETL_STRICT=0 after them (the env file sets it itself). A failed stage is reported and the next one starts; each invocation is one row in audit.migration_runs.

python3 tools/remote.py run 'ETL_SOURCE_SNAPSHOT=connect-YYMMDD-HHMM setsid nohup bash ops/run_etl_detached.sh \
  threeddx3 full 00_reference 05_ec2_statics 10_identity 20_pricing 30_orders 40_clinical 50_vouchers 60_workflow 70_operations 80_docs_comms 85_remaining 86_v3_additions 87_ec2_links 90_finalise \
  > etl-full.log 2>&1 < /dev/null &'
3

Watch it

Read the log through one ssh call at a time — never a polling loop that opens a session per poll.

python3 tools/remote.py run 'tail -60 etl-full.log; grep -c "=== .* stage" etl-full.log'

Then, connected to threeddx3:

SELECT run_id, status, started_at, finished_at, source_snapshot FROM audit.migration_runs ORDER BY started_at;
-- a step that read rows and wrote none is a defect until proven otherwise
SELECT stage, legacy_table, target_table, rows_read, rows_written, rows_skipped, status, message
FROM audit.migration_stage_results
WHERE status <> 'ok' OR (rows_read > 0 AND rows_written = 0)
ORDER BY started_at;
4

Mark the run of record

Only after reconciliation passes and is signed off. A CHECK allows is_authoritative only on a succeeded run; whether only one run may ever be authoritative is TO CONFIRM, so nothing enforces uniqueness.

UPDATE audit.migration_runs SET is_authoritative = true, notes = 'cut-over load, signed off by …'
WHERE run_id IN (…the runs of this pass…) AND status = 'succeeded';

4 · Reconciliation

minutes

Stage 90_finalise recomputes totals, validates NOT VALID constraints, refreshes the reporting views and reconciles. The definition (accepted 2026-10-13) is exact, with no tolerance:

for every legacy table:  source rows = rows migrated + rows excluded with a recorded reason

"Migrated" is the number of distinct legacy identities in each target whose legacy_source names the table; "excluded" counts audit.migration_exclusions. Tables not migrated at all pass with a table-level disposition (config.EXCLUDED_TABLES, mapping_spec.NO_TARGET_REASON, mapping_spec.CONSUMED_AS_REFERENCE; see the mapping). A target that holds more identities than the source (one row per department, per currency…) is reported as fan-out in notes, not clamped. Any fail row makes the run exit non-zero, which can gate a scripted cut-over.

-- the verdict
SELECT status, count(*) FROM audit.reconciliation_results WHERE run_id = :run GROUP BY 1;
-- what is unexplained
SELECT legacy_table, target_table, source_count, migrated_count, excluded_count, unexplained_count, notes
FROM audit.reconciliation_results WHERE status = 'fail' ORDER BY abs(unexplained_count) DESC;
-- why rows were excluded
SELECT legacy_table, reason_code, count(*) FROM audit.migration_exclusions GROUP BY 1, 2 ORDER BY 3 DESC;

Exclusion reasons allowed by the CHECK: parent_deleted, retired_table, unresolvable_reference, duplicate_source_row, security_policy, approved_other, pending_owner_decision (approved_other requires an approval_reference).

After reconciliation the stage logs these integrity counts (from etl/stage_90_finalise.py); each should be explainable:

  • orders with no items
  • order items whose order is missing
  • contacts with no legacy_id
  • users with no legacy_id
  • vouchers with a negative balance
  • voucher ledger vs balance mismatch
  • orders whose total does not match its items
  • archive packages with no items
  • tooth charts with no sites
  • orders with more than one active lock

5 · The anonymized copy

tens of minutes
1

Clone

tools/clone_db.py <source> <target> [--replace] uses CREATE DATABASE … TEMPLATE. The monitoring exporter keeps an idle session open on every database, so the tool terminates only idle sessions on the source and retries five times; it stops if the source has active sessions, and refuses to overwrite threeddx3.

python3 tools/remote.py run 'python3 tools/clone_db.py threeddx3 threeddx3_anony --replace'
2

Anonymize

ops/anonymize.py refuses any database but threeddx3_anony. Driven by compliance.data_classifications (generated from the comment tags), so a newly tagged column is covered without editing the script: per-patient random date shift of 30–365 days either way (intervals inside a case preserved), every classified column replaced by its deidentify_action, audit/event/PHI-access logs emptied and the chain head reset, a post-check that none of a sample of original values (hashes only, --sample, default 2000) survives, then VACUUM FULL ANALYZE. Exit 1 if the post-check finds anything.

python3 tools/remote.py run 'python3 ops/anonymize.py --db threeddx3_anony --yes'
3

Users and tests on the copy

python3 tools/remote.py run 'python3 ops/create_users.py'
python3 tools/remote.py run 'python3 tests/run_runtime_tests.py --db threeddx3_anony --quiet'

6 · Dumps

tens of minutes

Custom-format dumps of both databases, verified before they are trusted. Same pattern as ops/cleanup_and_retire_v1_v2.sh (root):

PG=dokku.postgres.shared-postgres; OUT=/var/tmp/backups; mkdir -p $OUT
export PGPASSWORD=$(cat /var/lib/dokku/services/postgres/shared-postgres/PASSWORD)
for db in threeddx3 threeddx3_anony; do
  f=$OUT/$db-$(date +%y%m%d).dump
  docker exec -i -e PGPASSWORD $PG pg_dump -U postgres -Fc -Z 6 $db > $f
  docker exec -i -e PGPASSWORD $PG pg_restore -l < $f | grep -c ' TABLE DATA '   # must be > 0
  sha256sum $f > $f.sha256
done

The backup login (member of threeddx3_backup: pg_read_all_data, BYPASSRLS, no write) can take the data dump instead of the superuser. The threeddx3 dump is a complete copy of PHI: store it encrypted and where the backup policy says; hand threeddx3_anony to anyone who does not need real data. Database-level role settings (ALTER ROLE … IN DATABASE … SET) and the roles themselves are not in a dump.

8 · Restore elsewhere

an hour

Ownership matters (SECURITY DEFINER gateways run as threeddx3_owner), so create the group roles before restoring and keep ownership. The statements below are generated from the catalog:

CREATE ROLE threeddx3_admin NOLOGIN BYPASSRLS;
CREATE ROLE threeddx3_app_rw NOLOGIN NOBYPASSRLS;
CREATE ROLE threeddx3_backup NOLOGIN BYPASSRLS;
CREATE ROLE threeddx3_etl NOLOGIN NOBYPASSRLS;
CREATE ROLE threeddx3_migrator NOLOGIN BYPASSRLS;
CREATE ROLE threeddx3_owner NOLOGIN BYPASSRLS;
CREATE ROLE threeddx3_read NOLOGIN NOBYPASSRLS;
GRANT threeddx3_owner TO threeddx3_admin;
GRANT pg_read_all_data TO threeddx3_backup;
GRANT threeddx3_migrator TO threeddx3_etl;
GRANT threeddx3_owner TO threeddx3_migrator;
createdb -U postgres -E UTF8 -T template0 threeddx3
pg_restore -U postgres -d threeddx3 --exit-on-error threeddx3-YYMMDD.dump
sha256sum -c threeddx3-YYMMDD.dump.sha256        # before restoring

Then create the logins with ops/create_users.py (it re-applies the per-database tenant defaults), run the runtime tests against the restored database, and verify the audit chain:

SELECT * FROM audit.fn_verify_chain();   -- first_broken_seq NULL = intact

9 · Partition maintenance

daily job

Range-partitioned tables, from the catalog:

tablekeypartitionsrange
audit.audit_logRANGE (occurred_at)25audit_log_2026_01 … audit_log_2027_12; catch-all: audit_log_default
audit.event_logRANGE (occurred_at)25event_log_2026_01 … event_log_2027_12; catch-all: event_log_default
audit.phi_access_logRANGE (occurred_at)25phi_access_log_2026_01 … phi_access_log_2027_12; catch-all: phi_access_log_default
comms.email_logsRANGE (sent_at)35email_logs_2017 … email_logs_2027_12; catch-all: email_logs_default, email_logs_pre2017

platform.fn_ensure_monthly_partitions(p_parent regclass, p_months_ahead integer) creates any missing monthly partitions for this month and the next p_months_ahead, each with a comment, and returns how many it made. Run it daily (a platform job); rows outside every partition land in the DEFAULT partition and stay queryable — a non-empty default partition means the job has not been running. Partitions are never dropped automatically: audit retention is not decided (compliance checklist).

SELECT platform.fn_ensure_monthly_partitions('audit.audit_log', 3);
SELECT platform.fn_ensure_monthly_partitions('audit.event_log', 3);
SELECT platform.fn_ensure_monthly_partitions('audit.phi_access_log', 3);
SELECT platform.fn_ensure_monthly_partitions('comms.email_logs', 3);
-- rows that fell through:
SELECT count(*) FROM audit.audit_log_default;

10 · Day two

ongoing

Changing the schema

  1. Add a new migration file (never edit an applied one — --status would report it as changed). Follow analysis/SCHEMA_CONVENTIONS.md: every object commented, nullable columns say what NULL means, PHI/PII tags at the end of column comments.
  2. A new tagged column needs its compliance.data_classifications row (V200 derived them from the tags) so the audit redacts it and the anonymizer replaces it.
  3. Rehearse on threeddx3_scratch_all, then python3 tools/build_docs.py --refresh-catalog --server.

Routine checks

SELECT * FROM audit.fn_verify_chain();                       -- tamper check of the audit trail
SELECT reporting.fn_refresh_materialized_views(true);        -- concurrent refresh of mv_*
SELECT event_code, count(*) FROM audit.event_log
 WHERE occurred_at > now() - interval '1 day' GROUP BY 1;    -- logins, failures, exports …
SELECT * FROM audit.phi_access_log ORDER BY occurred_at DESC LIMIT 50;

Retiring v1 and v2

Approved 2026-10-13. ops/cleanup_and_retire_v1_v2.sh (root, detached: sudo setsid nohup bash cleanup_and_retire_v1_v2.sh &) frees disk, then for threeddx2 and threeddx takes a pg_dump -Fc, verifies it has TABLE DATA entries, writes a .sha256, and only then drops the database — a dump that looks empty stops the script with the database still in place. The final dumps of 2026-10-13 are in v3/dumps/ with their checksums.

Troubleshooting

  • A query returns no rows. No tenant in the session: SELECT core.fn_set_tenant('3ddx'); then SELECT * FROM core.v_session_context;. RLS is fail-closed.
  • permission denied for table patient_identities. By design: use clinical.fn_get_patient_identity(id, purpose) or clinical.v_patients_masked.
  • The ETL refuses to start. PG_DB is not a v3 name, or a scratch target was not also named in ETL_ALLOW_SCRATCH (run_etl_detached.sh sets it for threeddx3_scratch_*).
  • A stage re-run fails on existing rows. Expected: rebuild from empty (phase 1).
  • clone_db: could not get the source free of sessions. An active session holds the source; wait and run once more.
  • UPDATE rejected on an approved / migrated record. By design: insert a new version with supersedes_id.
