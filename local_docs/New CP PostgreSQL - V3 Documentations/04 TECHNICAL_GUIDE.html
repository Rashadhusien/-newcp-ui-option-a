3 · Connect — the customer portal

The client-facing half, at 407 files, with Angular bundles layered over it for the newer screens (ng-connect, connect-facelift, newconnect-ui). A doctor can:

  • register an account, which notifies a sales supervisor for assignment;
  • submit a case — teeth chart, services, extras, files;
  • watch uploads, retry failures, and re-upload from an emailed link;
  • confirm a plan, a registration option, a restoration or a disclaimer;
  • download finished files and print a box label for a package they are sending;
  • see invoices, what is charged and what is outstanding, and their voucher balances;
  • cancel a case, but only where the stage still permits it.

What the portal offers is driven by the account's price list: an unchecked service is not shown at all. That makes the price list an access-control mechanism as well as a pricing one — a subtlety worth preserving deliberately rather than by accident.

6 · Identity, permissions and secrets

Two populations, two tables, two session models

Staff live in WSacounts (841 rows) with a role code in Type: 29 values from ADMIN and SUPER_ADMIN through CS, SALES, OPERATOR, PLANNER, RAD, LOGISTICS, QC, FINANCE, MARKETER to INACTIVE. Clients live in UserAcounts (41,642 rows).

CP authenticates with PHP sessions — the keys in use include uID, xty, xid, accType and _CP_SESSION_PASSWORD_EXP. The API authenticates with a JWT read from the body, a token header or a userCNToken cookie. A staff token carries agentID; a client token carries uID.

Page-scoped authorisation

// middlewares/authMiddleware.js
pageAuthorizedActions = parsedToken.authorizedActions
    .filter(a => a.task === req.headers.page)
    .map(a => a.action);

The token carries the whole permission set as {task, action} pairs; the request declares which page it is, and the API filters the set to that page. Two consequences follow. Revoking a permission does not take effect until the token is reissued. And the page name is part of the authorisation decision, so permissions are tied to the UI's structure rather than to the domain.

Card data

UserAcounts.CreditCard holds the card number under format-preserving encryption — FFX over AES-256, radix 10, so the ciphertext is the same length and shape as the number. CreditCardController exposes both directions, and the account read path decrypts and then masks to the last four unless the caller's page permissions include CC_View. Key and tweak come from AES_KEY and TWEAK in the environment. Alongside it sit three gateway vault references — CybersourceBillRekID, VersaPayVaultID, SkyLineVaultID — and ChargingSystem, which selects the gateway.

The migration's position

threeddx3 does not carry the card number across in any form. It takes the display label, the expiry and the vault token into billing.payment_methods, and leaves the ciphertext behind. Charging works from the vault token; nothing else needed the number. Passwords are treated the same way: legacy stores them reversibly encrypted, so none is migrated (user decision U3) — every migrated login has no hash and must set a new password through a reset.

Other secrets in the environment

AES_KEY, TWEAK, DBC, NODE_ENV, PASSWORD_EXPIRY_IN_DAYS, TEST_TOKEN, plus SECRET_KEY from the config module. Passwords expire on a configured interval, tracked as PasswordExpiryDate on clients and passwordExpiration on staff.

The pattern to notice

There is no integration boundary. 10 · What has to change

These are the structural problems, in the order they cost the business time. Each names what threeddx3 does instead — not as a claim that it is finished, but so the reasoning is inspectable.

One table, 627 columns

UserAcounts carries identity, contact details, configuration, credit-card data and roughly 450 price columns — one per product option per currency. Adding a currency or a product option means an ALTER TABLE on the busiest table in the system.

threeddx3 splits it into crm.contacts, iam.users, billing.payment_methods and pricing.price_lists / price_list_items, where a new option is a row.

Twelve parallel order tables

Orders holds sixteen foreign keys, one per product line, and each line has its own table with its own copy of cost, currency, billing, closure, revision and invoice columns. OrderSG alone has 208 columns. A question like what did this client spend last quarter? is a twelve-way union.

threeddx3 has one orders.order_items, with legacy_source recording which table each row came from, a parent item for iSmile stages and the services under a restoration, and a case above the orders.

Status is an integer with no lookup table

Status codes run 1–150 and are reused across product lines: 39 is Guide Design on a guide and In production on an appliance. The only decoder is connect/Enums.php and the OrdersFlow table, keyed on (status, order type, digital).

threeddx3 keeps the full vocabulary as workflow.workflow_states rows of one workflow definition per (order type, digital, service) — eighteen service dimensions, which v2 collapsed (review finding F05) — maps each legacy id through workflow.legacy_status_codes, and rolls them up to 16 canonical item statuses.

Dates are strings

dateSent, dateEnd, dateUpd, TimeBilled, closeDate are varchar(20) holding Unix epochs — sometimes "0", sometimes empty. OrderSG has a dateEndInt column that exists purely so the table can be sorted by date.

threeddx3 uses TIMESTAMPTZ for every instant and date for calendar dates such as a date of birth.

Five parallel history implementations

OrderHistory, service_status_history, PendingStatusHistory, OrdersInternalHistory and TaskHistory all record things that happened, in different shapes, with different column names, and none of them share a transition definition.

threeddx3 has one orders.order_status_history and one workflow.workflow_history, with transitions validated by a database function.

Business rules live in 82 triggers

The prevent_update_invoiced_* family — twelve near-identical triggers, one per order table — blocks edits to charged and invoiced rows, plus prevent_update_invoiced_orders_ctbb_credit on the header (which also maintains the voucher ledger) and two prevent_delete_charged_ismile_* triggers. The changelog shows 113 DROP TRIGGER against 82 CREATE TRIGGER: the rules are being rewritten repeatedly, one table at a time.

The rule underneath is two-level, and the distinction matters: charged freezes the whole line; invoiced freezes price, quantity, currency, billability and the patient's identity, while operational progress continues.

threeddx3 expresses it once, as orders.fn_reject_financial_edit on the single item table plus clinical.fn_reject_identity_edit_when_invoiced. That is separate from orders.fn_reject_when_locked, which governs concurrency — who is working on the order — not money.

SQL is written inline in page code

Roughly 9,600 SQL statements are embedded across 1,339 PHP files, against 200 distinct tables. There is no data-access layer, so a schema change means grepping the application.

Not a database problem, but it is the reason the schema cannot be changed incrementally — and the reason the migration is a rebuild rather than a refactor.

Card numbers are in the database

UserAcounts.CreditCard holds the full card number under format-preserving encryption; ServiceAPI decrypts it with AES-256 FFX and masks it to the last four unless the caller's token carries CC_View. The key and tweak come from AES_KEY and TWEAK in the environment.

threeddx3 does not carry the number across at all. billing.payment_methods stores a display label, an expiry and the gateway vault token — which is what charging actually needs.

Authorisation is baked into the token

The JWT carries an authorizedActions array of {task, action} pairs, and the API filters it by a page header. Permission changes therefore do not take effect until the token is reissued, and the page name is part of the security model.

threeddx3 models capability grants as data in iam.capabilities and iam.team_capabilities, so a change is immediate and auditable.

Backup tables in the production schema

orders_20250611, useracounts_2024-03-29, voucher_transaction_bkp_240104, servicefieldsprices_2024-03-29 and a dozen more sit alongside live tables, indistinguishable to a query.

The threeddx3 ETL excludes them explicitly, by name, in etl/config.py, and records each exclusion with its reason in audit.migration_exclusions.

11 · Designing the successor

Five properties of the current system are worth carrying forward deliberately, because they are correct and hard-won:

  • The service line is the unit of work. Not the order. Every workflow page, every SLA and every charge is per line. A design that makes the order the atom will be fighting the business immediately.
  • Locking is how concurrency is managed. One person owns a case while they work it, and the lock duration is the measurement the operations managers actually use.
  • Forms are configuration. Which questions a service asks is data, because new services arrive faster than releases do.
  • Price is per client, per option, per currency, per delivery mode. There is no such thing as the price of a guide.
  • Nothing physical happens before the doctor confirms. That gate is clinical and legal, not procedural.

And five that should not survive:

  • A table per product line.
  • Status as a bare integer whose meaning depends on which table you found it in.
  • Business rules as one trigger per table.
  • Configuration and pricing as columns on the account.
  • Permissions frozen into an issued token.

Where the shape of threeddx3 comes from

The 23 bounded contexts in the schema guide follow the departmental structure in section 2 of the business guide, because the departments are the real seams: CS, TP, Operations, Boston, Sales and Finance already own distinct data and hand it to each other at defined points. The contexts are those hand-off points made explicit.

Four roles bypass row-level security

Owner, migrator, admin and backup carry BYPASSRLS — the load writes across tenants, administrators must be able to repair, and a dump must contain every row. 12.4 · The audit trail is append-only and hash-chained

Tamper-evident trail of every row change on PHI, financial and regulated tables (HIPAA 164.312(b), 21 CFR Part 11 audit trail): one row per INSERT/UPDATE/DELETE of an audited row, or per TRUNCATE. The 'migrated' state

Legacy forms, reports, inspections and kit protocols were never approved under a Part 11 regime, so loading them as approved would claim a signature that never happened. 13 · Legacy findings of the v3 round

Facts about the legacy data established while building v3. Each corrected or completed something v2 assumed, and each is encoded in the ETL named under it — the text here is checked against that code every time this document is generated.

SubOrderServices.subOrderID is the id of the line, not of the order

The per-service records under a temporary restoration (order type 11), a final restoration (18) and an “other services” line (17) carry the id of the OrderRestoration / OrderOther row, reached from Orders.RestorationID, finalRestorationID and orderOtherID. Evidence: 5,183 of 5,185 comparable service/restoration pairs were sent the same day, while no Orders row whose ID equals a subOrderID carries a restoration. v2 joined subOrderID to Orders.ID and attached services to unrelated orders.

Consequence: the "1,394 parent-deleted children" of the v2 validation (owner question Q21) came from that join. With the correct join about 168 have no parent (63 temporary, 84 final, 21 other). The owners' disposition stands — true parentless children are excluded into audit.migration_exclusions — but the count is corrected.

Encoded in: etl/stage_30_orders.py (module docstring; services hung under their line via parent_item_id, key (subOrderID, serviceID, orderTypeID))

Price -1 is a sentinel, not a negative price

Every negative value in the legacy price tables (FieldsDefaultPrices, SGServicesDefaultPrices, SGServicesPrices, ServiceFieldsPrices) is exactly -1: 388,089 values on 2026-10-13. It reads as “no price for this mode” (digital vs manufacturing). threeddx3 stores NULL — neither a negative price nor a 0 that would read as free. The business meaning is still to be confirmed (see the open questions).

Encoded in: etl/stage_20_pricing.py _price(); measured by tools/probe_negative_prices.py (counts only)

Dates of birth are stored in three formats

How the legacy date of birth was stored before decoding: 'xchacha20' = libsodium XChaCha20-Poly1305-IETF ciphertext Base64(nonce || ciphertext) of Unix-seconds text (Q2); 'unix_seconds' = plain Unix-seconds number from older paths; 'date_text' = a plain date string. Migration provenance for reconciliation; the key and raw value are never stored. NULL = no DOB in the source (dob_status 'absent'), the DOB was entered in threeddx3, or a quarantined value matched none of the three formats.

The owners confirmed the encryption path (Q2): The encrypted DOB path uses libsodium XChaCha20-Poly1305-IETF AEAD, not credit-card FFX/AES-256. The application encrypts Unix-seconds text with a fresh 24-byte nonce and the 32-byte key loaded from hexadecimal SODIUM_KEY, then stores Base64(nonce || authenticated ciphertext). Only a successful authenticated decryption proves a value is ciphertext; shape is a hint. The key is read from LEGACY_DOB_SODIUM_KEY in the server-only secrets file, never logged, never stored. Whether the key supplied for the migration opens the production ciphertext is not yet established — tools/probe_dob_variants.py tests the plausible key forms on a sample, counts only. Until it is, ciphertext values are quarantined (DOB left NULL, case listed for manual resolution, no PHI in logs), never guessed; a re-run with the confirmed key updates the identities in place. Values that conflict between Orders and OrderRep are quarantined too.

Encoded in: etl/legacy_dob.py (DobDecoder), etl/stage_40_clinical.py; tools/probe_dob.py counts formats and outcomes

UserAcounts.doorType is a bitmask

CP tests it bit by bit: 1 registered, 2 CBCT door, 4 sales door, 8 contract door, 16 scan-centre leads. threeddx3 decodes it into five booleans on crm.contacts (is_registered, is_cbct_door, is_sales_door, is_contract_door, is_scan_center_lead), so “all CBCT doors” is a plain filter.

Encoded in: etl/stage_10_identity.py

UserAcounts.numberingSystem: 0 = Universal, 1 = FDI

Read from the CP option list (task22.php): {0: "universal", 1: "fdi"}; any other code is unknown and loads as NULL (tenant default). Storage is always FDI; the client's notation is display only. The column comment still reads “Migrated from UserAcounts.numberingSystem — decoded from the CP source (task22.php: 0 = Universal, 1 = FDI); any other legacy value loads as NULL” — the ETL now follows the CP source; Palmer is a valid choice for new data that legacy never produced.

Encoded in: etl/stage_10_identity.py; tooth conversion clinical.fn_universal_to_fdi / fn_fdi_to_universal

Archive timestamps are five hours early

Owner answer Q1: The legacy ArchivedPackages triggers subtract five hours. On insert they convert both CreationDate and UpdatedDate from +00:00 to fixed -05:00; on update they do the same only when the corresponding value changes. In the worked update, 2026-03-10 14:56:48 was stored as 2026-03-10 09:56:48. This is not DST-aware. Reverse the historical shift (+5 hours) for both fields during PostgreSQL migration; keep new writes in UTC and use America/New_York only for display.

The ETL adds 5 hours (ARCHIVE_TZ_OFFSET_HOURS, default 5) to both CreationDate and UpdatedDate of ArchivedPackages; new writes are UTC.

Encoded in: etl/stage_70_operations.py
