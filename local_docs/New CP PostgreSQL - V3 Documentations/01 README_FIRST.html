3D Diagnostix · threeddx3 · start here

Read this first

threeddx3 is the third and final PostgreSQL schema for 3DDX, replacing the legacy MySQL database connect. v2 was built, loaded and reviewed; v3 fixes the review findings (F01–F06), applies the owner answers, adds the new requirements, and is secured for PHI: fail-closed tenant isolation, PHI behind logged functions, a hash-chained audit trail. This page says what to read, in what order, and how to stand the database up.

Prerequisites

Dokku host

ssh as DEPLOY_SSH_USER, key DEPLOY_SSH_KEY

Everything heavy runs on the host, never through a tunnel. One multiplexed ssh connection (tools/cli.py) — never a retry loop: repeated logins lock the account.

PostgreSQL

18.3

The Dokku shared-postgres service. psql and pg_dump exist only inside the container (docker exec dokku.postgres.shared-postgres …); the tools use psycopg instead.

Legacy MySQL

database connect, snapshot 2026-10-13 03:00

Restored into dokku shared-mysql by ops/restore_mysql_connect.sh. The ETL only reads it.

Server Python

/var/tmp/etlvenv/bin/python (3.12)

psycopg and mysql-connector-python. tools/remote.py maps python3 to it.

Workstation Python

3.8 or newer

Only for tools/remote.py, the static checks and the document generators (standard library only).

Secrets

~/.3ddx3/ on the host, mode 600

secrets.env (SODIUM_KEY for the date-of-birth decoder; never logged), users.env (passwords issued by ops/create_users.py). The server copy of etl/connections.env holds the internal hosts and is never overwritten by a sync.

Build, migrate, load, anonymize — on the Dokku host

All commands are run from v3/ on the workstation and execute on the host through tools/remote.py. If ssh fails, stop and find out why; do not retry in a loop.

1

Configure the workstation side

Copy etl/connections.env.example to etl/connections.env (git-ignored) and set DEPLOY_SSH_HOST, DEPLOY_SSH_USER, DEPLOY_SSH_PORT, DEPLOY_SSH_KEY. Then load it in every shell that runs the tools:

cd v3
set -a; . etl/connections.env; set +a
2

Push the code to the host

tools/remote.py tars etl/ tools/ tests/ migrations/ ops/ 3ddx to /var/tmp/3ddx3 over one multiplexed ssh connection. Every run sources the server's etl/connections.env and ~/.3ddx3/secrets.env, and maps python3 to the server venv.

python3 tools/remote.py sync
python3 tools/remote.py run 'python3 tools/apply_migrations.py --status'
python3 tools/remote.py sync-run '…'      # both in one call
3

Create threeddx3 and apply the migrations

38 files, each in its own transaction, recorded with its SHA-256 in public.schema_migrations (an edited, already-applied file is reported as CHANGED SINCE APPLIED). tools/apply_migrations.py accepts only threeddx3, threeddx3_anony or threeddx3_scratch_<name>. ssh gives no terminal, so the drop confirmation must be given with --yes:

python3 tools/remote.py run 'python3 tools/apply_migrations.py --db threeddx3 --recreate-db --yes'

Other flags: --create-db (create if absent), --status, --to V090, --files V001,V002,V003. Authoritative loads always start from a recreated empty database: append-only history rejects DELETE, so a stage cannot be re-run over its own rows.

4

Verify the empty schema

On a scratch copy (scratch databases are disposable; --recreate-db needs no confirmation there):

python3 tools/remote.py sync-run 'python3 tools/apply_migrations.py --db threeddx3_scratch_all --recreate-db \
  && python3 tools/check_v3_catalog.py --db threeddx3_scratch_all \
  && python3 tools/check_on_conflict.py --db threeddx3_scratch_all \
  && python3 tests/run_runtime_tests.py --db threeddx3_scratch_all --quiet'

See the runbook for what each check proves.

5

Create the login users

Creates any missing login, attaches it to its group role, and for human users sets the tenant default in threeddx3 and threeddx3_anony (whichever exist). New passwords are 32 random characters, sent over the connection (never on a command line) and written to ~/.3ddx3/users.env (mode 600). Existing passwords are kept unless named with --rotate; aya and kyousry are never rotated here.

python3 tools/remote.py run 'python3 ops/create_users.py'
python3 tools/remote.py run 'python3 ops/create_users.py --rotate app backup'

Run it again after creating threeddx3_anony so its tenant defaults are set too.

6

Run the ETL, detached, on the host

ops/run_etl_detached.sh <target_db> <log_name> <stage> [stage …] runs each named stage with etl/run_etl.py --only, after sourcing connections.env and secrets.env; it exports ETL_STRICT=0 after sourcing (the env file sets it itself) and ETL_SOURCE_SNAPSHOT (default connect-261013-0300), recorded in audit.migration_runs. A threeddx3_scratch_* target is allowed through ETL_ALLOW_SCRATCH. Start it with setsid nohup so a dropped link cannot kill it:

python3 tools/remote.py run 'setsid nohup bash ops/run_etl_detached.sh threeddx3 full \
  00_reference 05_ec2_statics 10_identity 20_pricing 30_orders 40_clinical 50_vouchers 60_workflow 70_operations 80_docs_comms 85_remaining 86_v3_additions 87_ec2_links 90_finalise \
  > etl-full.log 2>&1 < /dev/null &'
python3 tools/remote.py run 'tail -40 etl-full.log'

7

Make the anonymized copy

Clone, then anonymize the clone in place. tools/clone_db.py refuses to overwrite threeddx3; ops/anonymize.py refuses any database but threeddx3_anony.

python3 tools/remote.py run 'python3 tools/clone_db.py threeddx3 threeddx3_anony --replace'
python3 tools/remote.py run 'python3 ops/anonymize.py --db threeddx3_anony --yes'
python3 tools/remote.py run 'python3 ops/create_users.py'

The anonymizer is driven by compliance.data_classifications: a per-patient date shift, every classified column replaced, the audit / event / PHI-access logs emptied, a post-check that no sampled original value survives (exit 1 otherwise), then VACUUM FULL ANALYZE.

8

Dump, hand over, document

Dumps of both databases, users and restore elsewhere are in the runbook. Regenerate this document set with python3 tools/build_docs.py (add --refresh-catalog after a migration change).

Roles and users

Group roles are created by V001 and granted by V130 (design: V3_DESIGN §C1). Nobody logs in as a group role; login users are members. Every object is owned by threeddx3_owner; PUBLIC has nothing. The comments below are read from the catalog.

group roleRLSpurpose
threeddx3_adminBYPASSRLSthreeddx3: full administrative access for named administrators (aya, kyousry). BYPASSRLS; every PHI read through the access functions is still logged.
threeddx3_app_rwsubject to RLSthreeddx3: create/read/update/delete on business tables under row-level security. Used by the web application (login app) and by user2_rw. No direct access to PHI identity tables; PHI is read through logged functions.
threeddx3_backupBYPASSRLSthreeddx3: reads every row for pg_dump (pg_read_all_data, BYPASSRLS). Cannot write anything.
threeddx3_etlLOGINthreeddx3 login; member of threeddx3_migrator. Created/managed by v3/ops/create_users.py.
threeddx3_migratorBYPASSRLSthreeddx3: applies migrations and runs the ETL. BYPASSRLS because the load writes across tenants; the only role allowed to set app.skip_audit.
threeddx3_ownerBYPASSRLSthreeddx3: owns every schema, table, function and view. NOLOGIN; nobody connects as it. Members (migrator, admin) act as owner through SET ROLE or inheritance.
threeddx3_readsubject to RLSthreeddx3: read-only access to business tables and PHI-masked views under row-level security (login user1_r).

The tenant setting — fail-closed

Every tenant-scoped table (225 of them) has row-level security enabled and forced, with one policy:

USING (tenant_id = core.fn_current_tenant()) WITH CHECK (tenant_id = core.fn_current_tenant())
-- core.fn_current_tenant() = NULLIF(current_setting('app.tenant_id', true), '')::bigint

No tenant, no rows

When app.tenant_id is unset the function returns NULL, the comparison is NULL, and the session sees nothing — and cannot insert. This is the opposite of v2, whose OR … IS NULL branch showed every tenant to an unscoped session (review finding F01). An empty result usually means a missing tenant, not missing data.

SELECT core.fn_set_tenant('3ddx');          -- raises on an unknown slug
SELECT * FROM core.v_session_context;        -- what this session will see

core.fn_set_tenant sets the value for the session. The application must call it (and core.fn_set_user) on every connection it takes from a pool. Human logins marked "app.tenant_id preset" above start inside the 3ddx tenant through ALTER ROLE … IN DATABASE … SET app.tenant_id; app, backup and threeddx3_etl do not. Roles with BYPASSRLS (owner, migrator, admin, backup) are not filtered at all. The only rows visible without a tenant are the global vocabulary rows of core.lookup_values and platform.feature_flags (SELECT only).

Patient names and dates of birth are not in any table the app or read roles can select: use clinical.fn_get_patient_identity(patient_id, purpose) (logged in audit.phi_access_log) or clinical.v_patients_masked.
