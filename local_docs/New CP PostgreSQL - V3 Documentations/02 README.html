threeddx3 — the final PostgreSQL schema

The third and final design for 3D Diagnostix (3DDX), built after the team reviewed v2 (Aya Adel, 2026-10-12, findings F01–F06) and answered the open questions. It targets a new database called threeddx3 on PostgreSQL 18 (Dokku shared-postgres); the legacy MySQL connect is read only, and threeddx2 is left as it was.

What changed from v2, in one paragraph

Tenant isolation is fail-closed: an unset app.tenant_id now sees no rows (v2's OR … IS NULL branch is gone, F01). Patient identity lives in clinical.patient_identities, readable only through logged functions (clinical.fn_get_patient_identity, every read written to audit.phi_access_log). The audit trail is hash-chained and verifiable (audit.fn_verify_chain). A case sits above orders, iSmile sub-orders and temporary/final restorations are child items, the voucher ledger is reconstructed with the legacy voucher_fill logic, and regulated records are versioned, signed and immutable once approved (or loaded as migrated). Reconciliation is source = migrated + excluded with zero unexplained rows. The full measured diff is in docs/V2_TO_V3_CHANGES.html.

Where things run

Everything heavy runs on the Dokku host, never through a tunnel (a statement costs ~1,000× more over ssh). One multiplexed ssh connection, through one tool:

set -a; . etl/connections.env; set +a              # git-ignored, never committed
python3 tools/remote.py sync                       # push etl/ tools/ tests/ migrations/ ops/
python3 tools/remote.py run 'python3 tools/apply_migrations.py --status'
python3 tools/remote.py sync-run '...'             # both

If ssh fails, stop and find out why. Never retry in a loop — repeated logins lock the account.

Build, load, anonymize — the short version

The exact steps, with prerequisites and what each one checks, are in docs/README_FIRST.html and docs/RUNBOOK.html. In outline, on the host:

python3 tools/apply_migrations.py --recreate-db          # threeddx3, from empty
python3 tests/run_runtime_tests.py --db threeddx3        # 264 assertions, rolls back
python3 tools/check_v3_catalog.py --db threeddx3         # conventions: 0 FAIL
ops/run_etl_detached.sh threeddx3 etl-run.log 00_reference 05_ec2_statics ...   # detached
python3 ops/create_users.py                              # login users -> group roles
python3 tools/clone_db.py threeddx3 threeddx3_anony
python3 ops/anonymize.py --db threeddx3_anony

An authoritative load always starts from a recreated empty database: append-only history rejects DELETE, so stages are not re-run over a populated database.

Before you query

Row-level security is fail-closed. A session with no tenant sees nothing:

SELECT core.fn_set_tenant('3ddx');
SELECT * FROM core.v_session_context;   -- confirms what this session will see

Human logins created by ops/create_users.py start inside the 3ddx tenant (ALTER ROLE … IN DATABASE … SET app.tenant_id); anyone else starts with zero rows.

Local checks (no database): check_ddl.py (every reference resolves), check_etl_sql.py (every ETL INSERT matches the schema), check_status_map.py (legacy status labels decode to the sixteen permitted codes), check_pricing_formulas.py (every rate a V203 formula names is created by stage 20), check_function_bodies.py (columns used inside plpgsql bodies exist), check_doc_links.py (every link between documents resolves).

Retired from v2 because they no longer test anything in v3: check_data_classifications.py (V200 now derives the classifications from the column tags), check_idempotency.py (v3 never re-runs a stage over a populated database), check_setnull_vs_check.py and check_fk_indexes.py (superseded by check_v3_catalog.py).

Non-negotiables

  • Never write to the legacy MySQL or to threeddx2. etl/config.py and

tools/apply_migrations.py refuse any target other than threeddx3, threeddx3_anony or a named threeddx3_scratch_*.

  • No passwords are migrated (U3): every migrated login must set a new one.
  • No PAN, no CVV, no reversible secret: credential_ref names an SSM key; tokens are hashes.
  • etl/connections.env and ~/.3ddx3/ on the host are never committed or logged.
  • The DOB decryption key lives only in ~/.3ddx3/secrets.env on the host.
