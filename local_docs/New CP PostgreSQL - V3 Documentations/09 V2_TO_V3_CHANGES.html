threeddx3 · v2 → v3

What Changed, and Why

v2 was loaded, verified and reviewed. Aya Adel's review of 2026-10-12 scored it 5/10 overall and 4/10 for accuracy, with “Not Ready Until Identified Blockers Are Resolved”: fail-open tenant isolation, no clean authoritative run, unimplemented order hierarchies and voucher reconstruction, collapsed workflow dimensions and empty fixation data. v3 answers those findings, the owner answers to the open questions, and the new requirements. Every figure below is measured from both codebases.

Why there is a v3

The review findings were not cosmetic. F01 (security and RLS) meant a session that forgot its tenant saw everything. F02 (authoritative run) meant the loaded database could not be proved to match the source. F03 (order completeness), F04 (voucher ledger), F05 (workflow mapping) and F06 (fixation and sleeves) were each data that v2 either lost or put in the wrong place. The owners answered the 21 open questions (8 answered, 6 closed, 3 in_review, 4 pending), and 24 new-requirement documents, the EC2 JSON catalogue, the OpenAPI contract and the core-function workbooks added structures v2 never had.

The same reasoning that produced v2 applies: the gaps were structural (PHI living inside the clinical record, a ledger that was replayed instead of reconstructed, no case above orders), so v3 is a consolidated rebuild with one migration per bounded context rather than V046+ patches on V001–V045.

Where these facts come from

v2: analysis/v2_final_schema_from_dump.sql (pg_dump of the deployed threeddx2) and v2/etl/. v3: docs/_catalog.json, the live catalog of a scratch database built from all 38 files in migrations/, and etl/. Reasons: review findings F01–F06, Aya's review (AR), owner answers Q1–Q21, input digests D1–D4 and user decisions U1–U11 as cited in analysis/V3_DESIGN.md. Re-run tools/gen_v2_v3_changes.py to re-measure.

The growth that matters is in rules, not tables: every constraint, index and column now carries a comment stating its business rule or query pattern, every constraint follows the naming convention, and the security posture moved from “fail-open with a helper” to “fail-closed and proven by test”.

Security and compliance

Tenant isolation became fail-closedF01, AR db_rules, C2

Why: F01 / Aya's review: “deployed RLS is fail-open when tenant context is unset”. In v2 every policy read tenant_id = core.fn_current_tenant() OR core.fn_current_tenant() IS NULL, so a session that forgot to set the tenant saw every tenant.

  • v2: 106 policies, 106 with the IS NULL escape; RLS forced on 106 tables.
  • v3: 227 policies on 225 tables, RLS forced on 225; 0 policies with an unset-tenant escape. An unset app.tenant_id makes core.fn_current_tenant() NULL, the comparison NULL, and the result zero rows.
  • 2 SELECT-only policies also admit rows whose own tenant_id is NULL — the global vocabulary rows of core.lookup_values and platform.feature_flags (INTEGRATION_LOG, core section). That is a global-row rule, not a missing-tenant rule.
  • Human read roles get app.tenant_id set per database role (C1), so a configured person starts inside the one tenant and anyone not configured sees nothing.
  • Runtime tests prove: unset → 0 rows; right tenant → rows; wrong tenant → 0 rows and INSERT rejected; the app role cannot bypass.

Roles were redrawn around least privilegeF01, C1, U6

Why: F01: the validation role bypassed RLS; AR asked for app-role isolation to be proven. v2 had three roles with broad grants and PUBLIC still had default rights.

  • v2 roles: threeddx_app, threeddx_etl, threeddx_readonly.
  • v3 group roles: threeddx3_admin, threeddx3_app_rw, threeddx3_backup, threeddx3_etl, threeddx3_migrator, threeddx3_owner, threeddx3_read — owner (NOLOGIN, owns everything), migrator (ETL, BYPASSRLS, the only role that may set app.skip_audit), admin (break-glass, BYPASSRLS), app_rw and read (under RLS), backup (pg_read_all_data).
  • Logins are members of those groups (app, user1_r, user2_rw, aya, kyousry, backup, threeddx3_etl), created by ops/create_users.py. PUBLIC has nothing on the database, schemas or functions.

Patient identity moved out of the clinical recordC3, Q2, U2, AR clinical_data

Why: HIPAA minimum necessary and GDPR pseudonymisation; AR clinical_data: “all 464,897 target patients lack source mapping” and the 2,944 populated DOBs collapsed to one value.

  • clinical.patients is now pseudonymous: id, tenant, a system-generated patient_code, owning contact and legacy keys.
  • clinical.patient_identities (1:1) holds name, DOB, sex, DICOM id and notes. It is granted to owner/admin only; the app reads it through clinical.fn_get_patient_identity / fn_list_patient_identities, SECURITY DEFINER functions that write audit.phi_access_log first.
  • clinical.v_patients_masked gives read roles initials and birth year only.
  • DOB is decoded by etl/legacy_dob.py from the three legacy shapes (XChaCha20-Poly1305 ciphertext, Unix seconds, date text), with dob_source_format and dob_status (decoded / absent / quarantined); the key is read on the server only and never logged.
  • Measured tags: 13 [PHI], 83 [PHI-RISK] and 79 [PII] columns, seeded into compliance.data_classifications by V200 and used for audit redaction and anonymisation.

The audit trail became tamper-evidentC4

Why: 21 CFR Part 11 needs secure, computer-generated, time-stamped audit trails that cannot be altered; v2's audit_log was append-only by convention only.

  • audit.audit_log is monthly partitioned and hash-chained: row_hash = sha256(prev_hash || canonical row), serialised by an advisory lock, head in audit.chain_heads; audit.fn_verify_chain(from, to) recomputes it.
  • PHI columns are written as "[redacted]" in old/new images, driven by compliance.data_classifications.
  • New partitioned logs: audit.event_log (logins, permission changes, exports, break-glass, consent and signature events) and audit.phi_access_log.
  • 70 tables carry the audit trigger; 27 are append-only by trigger.
  • app.skip_audit is honoured only for the migrator role, checked inside the trigger function (a runtime-test finding fixed in V100).

GDPR and FDA records got first-class tablesC5, C6, Q6, Q7, Q8, Q9, Q10

Why: New requirements and owner answers Q6–Q10: retention, legal holds, consents, subject requests, electronic signatures and traceability had nowhere to live.

  • GDPR: compliance.consents, subject_requests, processing_restrictions, legal_holds, versioned retention_policies (seeded inactive until approved, Q6), core.tenants.data_region.
  • Part 11 / 820: compliance.electronic_signatures (append-only, bound to record + version + content hash), compliance.trace_links (device history graph), compliance.role_appointments (Q7), compliance.break_glass_sessions, compliance.disclosure_rules (structure only, Q9).
  • Regulated records (docs.document_records, quality.inspections, production.reports, kit protocols) carry version_no, state, supersedes_id and content_hash; approved or migrated versions are immutable by trigger. Legacy rows load as migrated, which is immutable without claiming a Part 11 approval that never happened.

Cases sit above ordersQ3, U8, AR arch_split

Why: Q3 (owner: answered): no legacy case id exists; split-arch orders are paired by staff from patient, doctor, scanning centre and time. AR arch_split asked for an explicit case entity.

  • orders.cases (one per order by default, pairing_method single / auto_split_arch / manual, confidence, evidence) and orders.orders.case_id NOT NULL.
  • orders.case_pairing_candidates holds ambiguous pairs as pending for human review (U8) — nothing is auto-merged on weak evidence.

The order hierarchy is loaded the way legacy really stores itF03, Q21, AR sellable

Why: F03 / AR sellable: the iSmile one-to-three sub-order hierarchy and temp/final restorations were not implemented; 31,111 orders were itemless. Q21 (owner: closed) approved excluding true parent-deleted children.

  • order_items.parent_item_id, item_role (primary, ismile_suborder, refinement, temp/final restoration), restoration_stage.
  • Finding of this round: SubOrderServices.subOrderID is the id of the line row (OrderRestoration via RestorationID / finalRestorationID, OrderOther via orderOtherID), not Orders.ID. v2 joined it to Orders.ID and attached services to the wrong orders. With the correct join about 168 children have no parent (63 temp, 84 final, 21 other), not the 1,394 quoted in v2 and in the review.
  • OrderTrn and OrderOrtho are retired exclusions (Q21); every excluded row is written to audit.migration_exclusions with a reason code.
  • Unresolvable DocID orders (35) now belong to one placeholder “Unknown client” contact per tenant (crm.contacts.is_placeholder, U7) instead of being skipped.

Vouchers are reconstructed, not replayedF04, Q19, Q17

Why: F04 / AR db_rules: v2 replayed raw voucher_transaction rows, refused 27,733 movements and could not be re-run. Q19 (owner: answered) named voucher_fill.php as the rule.

  • Stage 50 ports fillVoucherRows() with Decimal arithmetic; every ledger row has a deterministic legacy_key, effective_at, sequence_no, scope (main / engel / service) and reconstruction_method = voucher_fill_v1.
  • Each transaction kind moves exactly one balance column, so remaining = issued − consumed − expired − refunded always holds (ck_vouchers__balance_consistent).
  • Engel counters are stored verbatim (legacy_cases_*) with no derived meaning (Q17 pending).

Workflow keeps all 18 legacy dimensionsF05

Why: F05 / AR workflow: v2 collapsed 18 (order type, isDigital, serviceID) dimensions into 16 and put every open item in the first definition's initial state.

  • One workflow_definitions row per service family and serviceID, with legacy_order_type_id, legacy_is_digital, legacy_service_id.
  • workflow.legacy_status_codes maps (definition, legacy status) → state; open items land in their own definition and state.
  • sla_minutes replaces sla_hours/sla_business_hours; task_due_date_changes requires a reason.

Fixation pins and sleeves are linked per order itemF06, Q16, D1

Why: F06 / Q16 (owner: answered): selections come from the JSON catalogues and are saved per order in SleeveArticleNumbersImplants / …Pins; v2's target was empty.

  • clinical.guide_sleeves and guide_fixation_pins hang off the order item, with catalogue id and version; clinical.sleeve_manufacturer_articles keys the JSON catalogue; surgical kits and versioned kit protocols are new (status unconfirmed, Q15).

Pricing defaults and the formula seed were correctedQ4, Q5, Q18

Why: Q5 (owner: closed): UserAcounts.uID = 0 is the default price reference; Q18 (owner: closed): offer50 is not an active rule.

  • pricing.price_lists.scope gains tenant_default (one list per currency from uID 0); an EXCLUDE stops overlapping active lists for the same scope.
  • V203 fixes a v2 defect: the per-implant-site prefix matched no item, so guides quoted 0.

Staff pairs became a relationship, not an external idQ20

Why: Q20 (owner: answered): opener and closer are both internal sales staff; v2's external_references mapping collapsed 21 pairs to 6.

  • iam.staff_relationships holds all 21 as sales_pair (meaning TO CONFIRM).

Archive timestamps are correctedQ1

Why: Q1 (owner: answered): the legacy triggers subtract a fixed five hours from both timestamps.

  • Stage 70 adds five hours to CreationDate and UpdatedDate; new writes are UTC.

New requirements got structuresD1, D2, D3, D4

Why: The 24 new-requirement documents (D3), the JSON catalogue (D1), the OpenAPI contract (D2) and the module/core-function workbooks (D4).

  • Relu AI planning (orders.order_item_ai_plans, integration.transfer_tasks), design decisions and confirmation links (Final AoX/FMP), item dependencies and assignments, pre-shipping instructions.
  • Uploads (catalog.item_upload_requirements, docs.document_links), notifications (comms.notification_rules, recipients, suppressions, signatures).
  • CRM: typed phones, equipment, competitors, feedback, sales targets, special-request categories; IAM: password history, work schedules.
  • Stage 05 loads the EC2 JSON statics with sha256 provenance; the DB twin is authoritative (U10).

ETL changes

v2's ETL was 16 files and 8,293 lines in 11 stages; v3's is 19 files and 12,447 lines in 14 stages.

One authoritative run from an empty databaseF02, INTEGRATION_LOG (orders decision)

Why: F02: the latest v2 run failed after earlier stages committed, and replay was unsafe for voucher balances and pinned by later foreign keys.

  • v3 loads only into a recreated empty database; stage re-runs on a populated database are not supported (stage 30 refuses to run over existing orders).
  • audit.migration_runs records source_snapshot, code_checksum and is_authoritative.

Reconciliation counts exclusions explicitlyF02, F03, Q21

Why: HANDOFF_V3 §8.2: v2 compared against raw source counts, so four tables read as failures when nothing was wrong.

  • audit.reconciliation_results: source = migrated + excluded, status = pass iff unexplained = 0.
  • audit.migration_exclusions is the ledger of every row deliberately not migrated, with a reason code (parent_deleted, retired_table, security_policy …).

Rows are counted where they landHANDOFF §4

Why: HANDOFF_V3 §4 patterns 1, 3 and 4: case-blind column checks, non-unique keys and ON CONFLICT counting suppressed rows as written hid ~590,000 lost rows in v2.

  • BatchWriter counts rows that landed and reports ON CONFLICT suppressions; any step that reads rows and writes none is flagged.
  • LEGACY_CONFLICT is the one upsert target, proved against a real unique index by tools/check_on_conflict.py; check_row_keys.py is case-exact.

No passwords, no reversible secretsU3

Why: U3: legacy passwords are not migrated.

  • iam.users.password_hash is NULL for every migrated user with must_change_password = true; a CHECK admits bcrypt/argon2id only.
  • iam.user_sessions stays empty; its token column is now a hash.

How v3 is applied

v2 grew to 45 incremental migrations, several of them fixes to earlier ones (V039–V045). v3 is a fresh, consolidated set: one file per bounded context (V004–V026), cross-schema foreign keys assembled into V090, rules in V100–V140, seeds in V200+. tools/apply_migrations.py applies them with psycopg (no psql on the host), one transaction per file, SHA-256 tracked in public.schema_migrations. tools/check_v3_catalog.py then checks the live catalog against SCHEMA_CONVENTIONS.md, and tests/run_runtime_tests.py proves the rules.

There is no in-place upgrade from threeddx2. v3 is a new database, threeddx3, built from the MySQL snapshot of 2026-10-13 from empty, because the ledger, the order hierarchy and the patient split cannot be reconstructed from v2's rows.
